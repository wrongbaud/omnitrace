# 7z

`src/discovery/validators/sevenzip.cpp` (validator `7z`), signature `7z` in
`signatures/core.toml` (format `7z`, category `container`), and
`src/containers/sevenzip/SevenZipReader.cpp` (reader `7z`). Both parse the
archive through `omnitrace::sevenzip`
([core/SevenZip.h](../../include/omnitrace/core/SevenZip.h)).

## On-disk layout (little-endian)

```
[ 32-byte signature header ][ packed streams ][ header ]
                                              ^ 32 + NextHeaderOffset
```

The signature header is the only thing at a fixed place:

| offset | field | notes |
|---|---|---|
| 0 | `magic[6]` | `37 7a bc af 27 1c` |
| 6 | `major`, `minor` u8 | `0.4` is what every 7-Zip writes |
| 8 | `StartHeaderCRC` u32 | CRC-32 of the next 20 bytes |
| 12 | `NextHeaderOffset` u64 | from the end of this header |
| 20 | `NextHeaderSize` u64 | |
| 28 | `NextHeaderCRC` u32 | |

So **one 32-byte read gives a CRC-verified extent**, which is why the
validator can size an archive exactly without touching the rest of it.

**A file does not own its bytes.** The header describes *folders*, each a
small graph of coders (LZMA2, LZMA1, Copy, BCJ, Delta, ...) turning packed
streams into one output stream, and that output is cut into *substreams*, one
per file. A folder has to be decoded whole to reach any file in it -- that is
what "solid" means, and why a 7z archive compresses better than a zip and
costs more to extract one file from.

The header is itself usually compressed (`kEncodedHeader`), so reading an
archive means decoding one small folder before anything can be listed.

Numbers in the header are variable-length: the first byte's high bits say how
many more follow. Bit vectors are most-significant-bit first, and most are
preceded by an "all are defined" byte.

## Identification

| tier | when |
|---|---|
| rejected | the six-byte magic with a start header that fails its CRC: a coincidence, not an archive |
| structural | the start header verifies (so the size is known) but the header does not parse, fails its CRC, or is encrypted |
| consistent | the header verifies and parses: entries, folders and coders are all on the finding |

There is no `verified` tier: the CRCs cover the headers, and checking the
contents means decoding them, which is the reader's job.

An archive with `-mhe=on` (encrypted header) reports
`7z-header-undecodable` at `structural` **with its exact size**, so it is
still carved and recorded as an encrypted archive rather than silently
dropped.

## The reader

Directories and empty files come straight from the header. Then each folder
is decoded once and sliced into its substreams, in file order.

Coders, and what happens to each:

| coder | handled |
|---|---|
| Copy | yes -- the identity, dropped from the chain |
| LZMA1 | yes, through liblzma's `LZMA_FILTER_LZMA1EXT` |
| LZMA2 | yes |
| Delta, BCJ x86/ARM/ARMT/PPC/IA64/SPARC/ARM64/RISC-V | yes, chained under liblzma |
| Deflate, BZip2 | yes, **on their own only** -- they come from zlib and libbz2, which cannot be chained with liblzma's filters |
| BCJ2 | no: four input streams, a graph this does not wire up |
| PPMd | no decoder in this build |
| AES-256 | no: encrypted |

**Why LZMA1 needs the extended filter.** 7z stores raw LZMA1 with the size in
the header and usually no end marker, so a plain `LZMA_FILTER_LZMA1` decoder
never reports the stream as finished -- and a BCJ filter above it holds back
the few bytes it cannot convert without lookahead until it hears that.
`LZMA_FILTER_LZMA1EXT` is told the output size and stops there, which flushes
the filter. Without it an LZMA1+BCJ folder comes out four bytes short.

**A stored folder with a byte filter over it** (7-Zip makes one for an
executable in a `-m0=Copy` archive) cannot go through liblzma at all: a raw
chain has to end in a compressor, and there is no way to ask for a lone BCJ
pass. The bytes are all there though, so they are emitted with
`filter_not_applied` naming the transform and `crc: unchecked`, and the entry
is marked truncated. A BCJ pass only rewrites the relative jump targets in
executable code, so that is a long way from nothing.

**Every substream carries a CRC-32**, so the entry's `crc` extra says `ok`,
`mismatch`, `none` (the archive stored none) or `unchecked` (the folder was
not decoded). A mismatch does not stop the bytes being emitted.

**A folder larger than `--max-file-bytes` is skipped**, with
`7z-folder-too-big`. A solid block has to be decoded whole, and this reader
holds it in memory rather than streaming it, so that bound is the one that
matters on a big archive. Raise it, or extract with 7-Zip.

## Attributes

From the validator: `version`, `header_offset`, `header_size`,
`header_encoded`, `coders`, `folders`, `entries`, `files`, `directories`,
`unpacked_bytes`, and `undecodable_folders` when non-zero. From the reader:
`version`, `header_encoded`, `folders`, `entries`, `coders`, plus `bad_crcs`
and `skipped_folders` when non-zero. Meanings: `docs/reference/ATTRS.md`.

## Diagnostics

| code | severity | meaning |
|---|---|---|
| `7z-truncated` | warning | the header ends past the available data |
| `7z-bad-header` | warning | the header did not parse |
| `7z-header-crc-mismatch` | warning | the header does not match its CRC |
| `7z-header-undecodable` | warning | the header is compressed or encrypted with something this build cannot decode |
| `7z-unsupported-coder` | info / warning | a folder uses a coder this build does not decode; its entries are listed with no contents |
| `7z-filter-not-applied` | warning | a stored folder's byte filter could not be run; the bytes are emitted with it still applied |
| `7z-folder-too-big` | warning | a solid folder is past `max_file_bytes` |
| `7z-folder-decode-failed` | warning | a folder did not decode |
| `7z-crc-mismatch` | warning | a file does not match the CRC the archive stored |
| `7z-bad-entry` | warning | the file list and the substream list do not agree |
| `7z-limit-entries` | warning | `max_nodes_per_fs` stopped the walk |

## Not yet supported

* **BCJ2**, which takes four input streams. 7-Zip uses it at `-mx9` on
  executables, so a high-compression archive of a firmware tree will have one
  folder this cannot decode. Everything else in such an archive still comes
  out.
* **PPMd**: no decoder here.
* **Encrypted archives** (AES-256). An encrypted *header* is reported and the
  archive still sized and carved; encrypted *contents* with a plain header
  are listed with their names and sizes and no data.
* **Deflate or BZip2 chained with a byte filter**, for the reason above.
* Streaming a folder larger than memory.

## Verified on

Eleven archives from 7-Zip 26.03, every file compared byte for byte with the
original:

* `-mx5` default (LZMA2, and LZMA2+BCJ for the executable), `-m0=LZMA`,
  `-mhc=off` (plain header), `-mf=BCJ`, `-m0=Delta`: every file matches.
* `-m0=Copy`: three files match; the executable's folder is Copy+BCJ, and it
  comes out at its full 43320 bytes with `filter_not_applied: bcj-x86`.
* `-m0=Deflate` and `-m0=BZip2`: three of four match; the fourth is that
  coder chained with BCJ, which is listed with no contents.
* `-ms=on -mx9`: three of four match; the fourth is in the BCJ2 folder.
* `-m0=PPMd`: all four listed, none extracted, `7z-unsupported-coder`.
* `-p... -mhe=on`: `structural` with the exact archive size and
  `7z-header-undecodable`.
