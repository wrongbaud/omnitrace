# Omnitrace v2 - An Embedded Systems Analysis Suite

# Problem Statements

Many forensic examiners are trained on how to analyze data extracted from mobile devices, however when it comes to embedded devices many rely on one-off scripts, tools like binwalk and manual analysis. Omnitrace will aim to solve that problem by acting as an open-source embedded systems forensic analysis suite. 

The goal is to allow users to upload SPI/eMMC/I2C dumps and attempt to perform a forensic analysis of the underlying filesystem and flag specific things for evidence. It should handle traditional forensic capabilities like MD5 hashing, report generation and data recovery/extraction from deleted files. 

Ideally this tool will be cross platform and able to run on Windows/Linux/MacOS. The core development should be done in C++ for increased spead

# MVP Features

## Phase 1

The baseline feature set should allow for the following:

1. Upload forensic image
    - SPI Flash/eMMC/Tar/Zip, etc
2. Perform initial analysis of firmware image (identify partitions,or unzip/untar recursively until an image or filesystem is found)
    - Goal: Develop extraction capabilities that have parity with unblob,binwalk and moria
3. List and extract partitions from the image or tarball
    - The output of this should be markdown and yaml for additional agents to consume


## Phase 2

4. Using a set of pre-determined metrics search for data that could contain forensically valuable information
    - MAC Addresses
    - Device Logs
    - Connection History
    - PII
5. Generate a polished report using the report generation code from the /home/wrongbaud/projects/omnisonde directory
    - Sub goal - develop standalone library for omnisonde syle report generation

# Development Notes and Instructions

# Project state and where things are (maintained; last updated 2026-09-23)

- Phases 0-2 are complete. Phase 1's parity criterion (>= 95% files recovered vs unblob and moria) has been **measured and is met**: over 33 images (20 fixtures, 13 corpus, including a 3.8 GB and a 7.8 GB eMMC), **99.9% of moria and 95.1% of unblob** by distinct regular-file contents, and **100% of fixture ground truth** (179/179 contents, every file of every fixture) (`docs/PARITY.md`, `tests/parity/sweep.py`). The unblob figure was 65.7% when first measured; reading SquashFS v1-v3 closed the gap. `docs/ROADMAP.md` is the short form and states what is registered *today* (it defers the per-format table to the generated `docs/reference/FORMATS.md` so it cannot go stale); `DEVELOPMENT_PLAN.md` is the long form.
- What works end to end: 56 signatures over 40 format ids, 32 validators, 11 filesystem readers (squashfs, ext2/3/4, jffs2, qnx6, qnx-ifs, ubifs, yaffs2, cramfs, romfs) and 18 container formats read by 12 readers (gzip, bzip2, xz, lzma, lz4, zstd, lzop, tar, cpio, zip, 7z, uimage, fit, ubi, android-boot, android-vendor-boot, android-sparse, android-super). Every format with a signature now has a reader, filesystems included. The corpus holds no cramfs or romfs image -- the audio `romfs` hit is `-rom1fs-` inside a blkid magic table -- so those two are tested against built images, `mkfs.cramfs -N big|little` for one and an in-test writer for the other. `--history` recovers superseded and deleted versions for ext, JFFS2, QNX6, UBIFS and YAFFS2, and superseded logical erase blocks for UBI. Every filesystem in the MVP list now has a reader.
- **Measuring parity found two real gaps and one metric trap; read `docs/PARITY.md` before quoting a number.** (1) **FAT was not identified at all** and was the *entire* difference from ground truth; now fixed. FAT12/16/32 are identified, sized and read, with deleted-file recovery under `--history`. The format has **no magic**: the signature matches the file-system type string, which the spec says "is not required to be correct", so it is a screen and the BPB decides everything -- three corpus images carry `FAT32   `/`FAT12   `/`FAT16   ` within twenty bytes of each other, a driver's string table the validator rejects on geometry. The type is the cluster count, never the string. Deleting stamps 0xE5 over the name's **first byte** and frees the chain, so a recovered file is read contiguously (right only if it was never fragmented -- `fat-deleted-unchained` says so) and its first character is unrecoverable without a long-name entry, shown as `_`. A superseded version leaves nothing at all: the freed dirent is reused by the next write. `docs/formats/fat.md`. (2) **SquashFS v1-v3 was detected and then dropped** -- the validator parsed v4 only, so a v3 finding carried `extent: unknown` and was never handed to a reader, losing 3,903 contents (72% of the unblob shortfall) to one missing extent. **Now fixed**: v1-v3 are sized and read, and that image went 0.1% -> 98.8%. Its layout is in `docs/formats/squashfs.md` and every offset there was read off evidence, because the published structs are bitfields whose wire layout the compiler chooses -- the directory header is 9 bytes, not the 8 the struct reads as, and 8 yields garbage after the first entry. v1-v3 also record no compressor, so one is found by decoding the first metadata block (`squashfs-compression-probed`); DD-WRT/Broadcom LZMA1 with a five-byte header and no end marker is the common answer and `kFilterLzma1Ext` decodes it when told the size, which squashfs always knows. (3) **`ar` static libraries are not opened** -- 1,224 of unblob's 1,229 extra contents on the auto-ivi eMMC. The rest of the unblob gap is unblob carving individual ELFs out of decompressed blobs, which is a policy difference, not missing data. The metric trap: **counting symlinks makes tools look different when they are not**, because a link's target resolves against the directory it is in and every tool nests extractions under its own prefix -- that artifact alone read as 226 missing files on an image that is at 100%. Count distinct regular-file contents by sha256, and report zero-filled blobs separately (28 of moria's 30 "wins" on router.bin are files it could not reconstruct).
- **Nested analysis is the thing to understand before changing the driver.** Every file a walk writes is re-scanned and analysed again when it is itself an image, so chains resolve to the end: `boot.img -> ramdisk -> gzip -> cpio -> rootfs`, `uImage -> lzma -> kernel`, `.tar.gz -> tar -> squashfs`. `descend_into_file` and `process_container` in `src/discovery/Recurse.cpp`; bounded by `Limits::max_depth`.
- Two rules there earn their keep and are easy to undo by accident: a finding is only descended into when it is a filesystem/partition at Structural+ and at least `min_region_bytes`, or a container whose format has a registered reader; and a structure a validator walked but could not size carries `extent: unknown` and is never handed to a reader. Both exist because an eMMC image holds hundreds of accidental magics.
- Every stream format now reports what its payload is worth: `compress::stream_check` names the check the header declares and the entry carries `checksum` = `ok`/`mismatch`/`none`/`unchecked`. The rule that made it useful is that a **checksum mismatch is not a decode failure**: the bytes decoded to the stream's natural end, so the validator still sizes it and the reader still emits it (`decompress-checksum-mismatch` is the only failing Status that leaves a full result in `out`). Undoing that would bury a damaged stream under an "unidentified" region -- the router-wrt corpus image has exactly one.
- A word-swapped image is analysed through a view that exists only in memory, so `analyze` writes that view to `flash/<stem>-swap32.bin` (`write_corrected_view` in `src/discovery/Recurse.cpp`, `AnalyzeOptions::write_corrected_view`, hashes in `flash/SOURCE.yaml` under `corrected:`). Every offset in the manifest and every carved byte is an offset into *that* file, not the evidence -- which is why it has to exist.
- Unidentified regions are profiled by `omnitrace::entropy` (`core/Entropy.h`) and carry `entropy`/`entropy_chi2`/`entropy_class`. The class is deliberately hedged: `random` means "compressed or encrypted", never "encrypted", because xz output is statistically identical to AES (chi2/df 0.995 vs 0.971 -- measured, in `docs/formats/entropy.md`). Do not add a threshold that claims a cipher; the useful signal is high entropy *plus* no magic anywhere in the region.
- cramfs bitfields flip with endianness, not just byte order: GCC packs them from the opposite end on a big-endian target, so a BE image is *not* a byte swap of an LE one (`read_inode` in `CramfsReader.cpp` spells out both). Its offsets count 4-byte units, so every structure is 4-aligned.
- A format with a strong magic that a reader can open belongs in `src/core/Swap.cpp`'s veto table. Without an entry, a small high-entropy file of that format (a bare `.bz2`) falls through to the text score, is analysed word-swapped, and is lost whole.
- **A checksum is what turns a weak magic into an extent.** Four formats now share the rule and it is the one to reach for next time: a GPT header whose signature was cleared is read because its CRC32 covers the signature bytes (`gpt-cleared-sig`); an unterminated tar claims only the bytes whose member headers verified; an Android super's partition map is described but claims nothing until the SHA-256 over its tables matches; and romfs refuses what its own validator refused. The shared failure they prevent is a magic-tier guess becoming bytes on disk -- romfs carved 1.87 GiB out of a blkid magic table before it applied this. A reader must re-apply its validator's rule rather than trust its caller.
- `analyze` will not fill the disk it writes to. `disk_headroom()` (`discovery/Recurse.h`) holds back 5% of free space, minimum 256 MiB; the extraction budget is cut once up front (`analyze-limit-disk`) and each carve is checked as it comes (`carve-limit-disk`), because `--max-carve-bytes` is per file and nothing else bounds carving in aggregate. The measurement is of the filesystem holding `--out`, which on a dev box is often tmpfs -- a case directory under `/tmp` fills RAM, which this project has already done once.
- **Phase 2 is complete.** Four post-analysis layers now run after `analyze()` builds the graph, and all of them depend on `core` (plus `output`) and never on `discovery` -- they take a list of `(node id, entries)` pairs, so a finished case can be re-examined without re-extracting it. `rules` (search packs) -> `analyzers` (what kind of system is this: Linux, QNX, Android) -> `artifacts` (parse a known file type into records: certificates) -> `report` (a typed Document rendered to HTML/Markdown, with the evidence re-hashed first). `docs/{RULES,ANALYZERS,ARTIFACTS,REPORT}.md`.
- **That decoupling is now spent rather than latent.** `output::load_case_listings` reads a case directory back into entries, and `omnitrace report <case>` re-runs the analyzers and the extractors over them -- six of seven sections, all but search hits, which want the image rather than the case. On the router corpus the Platforms and Extracted artifacts sections come back byte-identical to the ones `analyze` wrote. Two rules decide where an entry's bytes come from and both were found by watching the wrong thing happen: **the file beside the listing wins** over a recorded `host_path` that also exists (a case is routinely *copied*, and trusting the recorded path read the original's files while reporting on the copy), and **a path outside the case is never followed** (a case whose `files/` had been deleted produced records parsed out of a different case's bytes). The containment check is a path test, not a string prefix -- `<case>-copy` sits next to `<case>`. `docs/CASE_LAYOUT.md`, "Reading a case back".
- **A report is data, never a concatenated string.** `src/report/` builds a typed `Document` and renders it once, because the previous generation shelled out to pandoc and that failed on provenance, escaping and determinism. A device's own bytes reach the markup: a partition named `<script>` and a certificate subject with a pipe in it are both attacker-controlled, and the renderers escape for their own format.
- Phase 2 has started with `src/rules/`: YAML search packs (`rules/*.yaml`, embedded like `signatures/*.toml`) compiled into one RE2 set. RE2 rather than `std::regex` because a pack is untrusted input and a backtracking engine can be hung by `(a+)+$`; it brings Abseil, which FetchContent builds in ~10s. Tune a new rule against the corpus before shipping it -- the first draft fired 581 times on one router's JavaScript (`docs/RULES.md`).
- **Sizing validators are the performance risk.** A validator that walks or decodes to find a structure's end runs on every magic hit, most of which are false. Screen the header cheaply first and read any forward search in chunks -- an unscreened byte-by-byte search took a scan of the QNX corpus from 12s to 2m49. `src/discovery/validators/zip.cpp` is the worked example.
- The contract every change must follow is `docs/ARCHITECTURE.md`. Read it before writing code. `docs/CODE_TOUR.md` explains the layers; `docs/EXTENDING.md` has step-by-step how-tos (validator, filesystem reader, container reader, CLI command, fixture, diagnostic code).
- Build: `cmake --preset linux-gcc && cmake --build --preset linux-gcc --parallel && ctest --preset linux-gcc`. Also keep `linux-clang` and `linux-asan` green. `CONTRIBUTING.md` covers setup on all OSes.
- Public headers under `include/omnitrace/` are the interfaces. Per-layer CMake globs sources and tests, so adding a file never needs a CMake edit.
- Output contract: the case directory in `docs/CASE_LAYOUT.md` (INFO.yaml, INFO.md, flash/, partitions/, mount.sh). `docs/reference/` holds generated catalogues (diagnostics, formats, attrs, CLI flags); regenerate with `scripts/gen_docs.py`, check with `scripts/check_docs.py`.
- Decisions on record: no web UI until the core is proven (`core-before-ui`); moria is a design reference and parity baseline only, never a dependency (`docs/MORIA_SPIKE.md`); GPT labels name carved partitions, nested finds are named by offset; third-party dependencies are allowed when they static-link (bzip2 was added on that basis; `vcpkg.json` plus a `find_package` in `cmake/Deps.cmake` plus the layer's `omnitrace_module(... DEPS ...)` plus a row in `CONTRIBUTING.md`).
- A parser two layers need lives in `src/core/` (`omnitrace::fdt` in `core/Fdt.h` is the worked example: the `dtb`/`fit` validators score a tree, `FitReader` extracts from it). A code assigned there and emitted from another layer is fine -- `scripts/gen_docs.py` joins the two halves across files.
- Diagnostic codes and attrs keys must be **literal** in the source. `scripts/gen_docs.py` cannot see a code built at run time (`format_ + "-failed"`), so it would reach manifests uncatalogued; use a layer-scoped literal (`container-decompress-failed`) when one reader serves several formats.
- `corpus/` is a local, git-ignored evidence corpus. Never commit images. Testing against it is described in `docs/TESTING.md`.
- **A regression check that compares nothing passes.** Three times in one session a corpus comparison reported success while both sides were empty: a `--max-bytes` too small for the nested nodes to exist, then a parser keyed on `format: tar` when the hits resolve as `also-matched`. Make the comparison hash the whole normalised manifest and refuse to report success when it found none of the thing under test.
