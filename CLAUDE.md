# Omnitrace v2 - An Embedded Systems Analysis Suite

# Problem Statements

Many forensic examiners are trained on how to analyze data extracted from mobile devices, however when it comes to embedded devices many rely on one-off scripts, tools like binwalk and manual analysis. Omnitrace will aim to solve that problem by acting as an open-source embedded systems forensic analysis suite. 

The goal is to allow users to upload SPI/eMMC/I2C dumps and attempt to perform a forensic analysis of the underlying filesystem and flag specific things for evidence. It should handle traditional forensic capabilities like MD5 hashing, report generation and data recovery/extraction from deleted files. 

Ideally this tool will be cross platform and able to run on Windows/Linux/MacOS. The core development should be done in C++ for increased spead

# MVP Features

## Phase 1

The baseline feature set should allow for the following:

1. Upload forensic image
    - SPI Flash/eMMC/Tar/Zip, etc
2. Perform initial analysis of firmware image (identify partitions,or unzip/untar recursively until an image or filesystem is found)
    - Goal: Develop extraction capabilities that have parity with unblob,binwalk and moria
3. List and extract partitions from the image or tarball
    - The output of this should be markdown and yaml for additional agents to consume


## Phase 2

4. Using a set of pre-determined metrics search for data that could contain forensically valuable information
    - MAC Addresses
    - Device Logs
    - Connection History
    - PII
5. Generate a polished report using the report generation code from the /home/wrongbaud/projects/omnisonde directory
    - Sub goal - develop standalone library for omnisonde syle report generation

# Project state and where things are (maintained; last updated 2026-09-23)

- Phases 0-2 are complete. Phase 1's parity criterion (>= 95% files recovered vs unblob and moria) is **measured, met and complete**: over all 35 images -- 20 fixtures and the whole 15-image corpus, up to a 15.7 GB eMMC -- **99.9% of moria and 99.5% of unblob** by distinct regular-file contents, and **100% of fixture ground truth** (179/179). The one image below 95% of moria is the QNX unit, where the ratio is meaningless: neither baseline reads QNX6/QNX-IFS, so omnitrace recovers **62,352** contents against unblob's 8 and moria's 11, and "62.5% of unblob" is five of eight. What it still misses there is seven gzipped QNX slog device logs whose bytes are **not reachable through the filesystem at all** -- a byte-exact search across all 105,951 extracted files (20.2 GB) finds none of them. Reading bytes a filesystem's metadata has stopped claiming is free-space carving, a capability that does not exist yet, not a broken reader. Report the denominator whenever a share looks bad (`docs/PARITY.md`, `tests/parity/sweep.py`). The unblob figure was 65.7% when first measured; reading SquashFS v1-v3 closed the gap. `docs/ROADMAP.md` is the short form and states what is registered *today* (it defers the per-format table to the generated `docs/reference/FORMATS.md` so it cannot go stale); `DEVELOPMENT_PLAN.md` is the long form.
- What works end to end: 56 signatures over 40 format ids, 32 validators, 11 filesystem readers (squashfs, ext2/3/4, jffs2, qnx6, qnx-ifs, ubifs, yaffs2, cramfs, romfs) and 18 container formats read by 12 readers (gzip, bzip2, xz, lzma, lz4, zstd, lzop, tar, cpio, zip, 7z, uimage, fit, ubi, android-boot, android-vendor-boot, android-sparse, android-super). Every format with a signature now has a reader, filesystems included. The corpus holds no cramfs or romfs image -- the audio `romfs` hit is `-rom1fs-` inside a blkid magic table -- so those two are tested against built images, `mkfs.cramfs -N big|little` for one and an in-test writer for the other. `--history` recovers superseded and deleted versions for ext, JFFS2, QNX6, UBIFS and YAFFS2, and superseded logical erase blocks for UBI. Every filesystem in the MVP list now has a reader.
- **Measuring parity found two real gaps and one metric trap; read `docs/PARITY.md` before quoting a number.** (1) **FAT was not identified at all** and was the *entire* difference from ground truth; now fixed. FAT12/16/32 are identified, sized and read, with deleted-file recovery under `--history`. The format has **no magic**: the signature matches the file-system type string, which the spec says "is not required to be correct", so it is a screen and the BPB decides everything -- three corpus images carry `FAT32   `/`FAT12   `/`FAT16   ` within twenty bytes of each other, a driver's string table the validator rejects on geometry. The type is the cluster count, never the string. Deleting stamps 0xE5 over the name's **first byte** and frees the chain, so a recovered file is read contiguously (right only if it was never fragmented -- `fat-deleted-unchained` says so) and its first character is unrecoverable without a long-name entry, shown as `_`. A superseded version leaves nothing at all: the freed dirent is reused by the next write. `docs/formats/fat.md`. (2) **SquashFS v1-v3 was detected and then dropped** -- the validator parsed v4 only, so a v3 finding carried `extent: unknown` and was never handed to a reader, losing 3,903 contents (72% of the unblob shortfall) to one missing extent. **Now fixed**: v1-v3 are sized and read, and that image went 0.1% -> 98.8%. Its layout is in `docs/formats/squashfs.md` and every offset there was read off evidence, because the published structs are bitfields whose wire layout the compiler chooses -- the directory header is 9 bytes, not the 8 the struct reads as, and 8 yields garbage after the first entry. v1-v3 also record no compressor, so one is found by decoding the first metadata block (`squashfs-compression-probed`); DD-WRT/Broadcom LZMA1 with a five-byte header and no end marker is the common answer and `kFilterLzma1Ext` decodes it when told the size, which squashfs always knows. (3) **`ar` static libraries were not opened** -- 1,224 of unblob's 1,229 extra contents on the auto-ivi eMMC; now read (93.4% -> 99.8% on that image). Its names are the trap: `/108` is an offset into the `//` string-table member and `#1/13` puts the name in the first 13 data bytes, and a cross toolchain's libgcc.a is 1,771 members of which every one is a `/N`. The symbol (`/`) and string (`//`) members are not files. It reaches **Verified** deliberately: absorbing nested findings needs *strictly higher* confidence (`outranks` in Scan.cpp), and at Consistent a static library's hundreds of ELF members were each reported as a separate top-level region on top of the files the reader extracts. (4) **A structure inside a payload had no digests.** A find inside an extracted file was never carved -- "reachable through its extraction" -- but that only holds when it *is* the file. One dongle's xz payload is 222 complete ARM shared objects that were located, sized and typed and had no hash, so they could not be matched against a known-file set; they are carved now. Measure "the whole of it" against `file.size`, **never** the File node's `location.length`, which is a position in the enclosing structure -- getting that wrong carved a byte-identical second copy of 52 tarballs out of one router image. The metric trap: **counting symlinks makes tools look different when they are not**, because a link's target resolves against the directory it is in and every tool nests extractions under its own prefix -- that artifact alone read as 226 missing files on an image that is at 100%. Count distinct regular-file contents by sha256, and report zero-filled blobs separately (28 of moria's 30 "wins" on router.bin are files it could not reconstruct).
- **Nested analysis is the thing to understand before changing the driver.** Every file a walk writes is re-scanned and analysed again when it is itself an image, so chains resolve to the end: `boot.img -> ramdisk -> gzip -> cpio -> rootfs`, `uImage -> lzma -> kernel`, `.tar.gz -> tar -> squashfs`. `descend_into_file` and `process_container` in `src/discovery/Recurse.cpp`; bounded by `Limits::max_depth`.
- Two rules there earn their keep and are easy to undo by accident: a finding is only descended into when it is a filesystem/partition at Structural+ and at least `min_region_bytes`, or a container whose format has a registered reader; and a structure a validator walked but could not size carries `extent: unknown` and is never handed to a reader. Both exist because an eMMC image holds hundreds of accidental magics.
- Every stream format now reports what its payload is worth: `compress::stream_check` names the check the header declares and the entry carries `checksum` = `ok`/`mismatch`/`none`/`unchecked`. The rule that made it useful is that a **checksum mismatch is not a decode failure**: the bytes decoded to the stream's natural end, so the validator still sizes it and the reader still emits it (`decompress-checksum-mismatch` is the only failing Status that leaves a full result in `out`). Undoing that would bury a damaged stream under an "unidentified" region -- the router-wrt corpus image has exactly one.
- A word-swapped image is analysed through a view that exists only in memory, so `analyze` writes that view to `flash/<stem>-swap32.bin` (`write_corrected_view` in `src/discovery/Recurse.cpp`, `AnalyzeOptions::write_corrected_view`, hashes in `flash/SOURCE.yaml` under `corrected:`). Every offset in the manifest and every carved byte is an offset into *that* file, not the evidence -- which is why it has to exist.
- Unidentified regions are profiled by `omnitrace::entropy` (`core/Entropy.h`) and carry `entropy`/`entropy_chi2`/`entropy_class`. The class is deliberately hedged: `random` means "compressed or encrypted", never "encrypted", because xz output is statistically identical to AES (chi2/df 0.995 vs 0.971 -- measured, in `docs/formats/entropy.md`). Do not add a threshold that claims a cipher; the useful signal is high entropy *plus* no magic anywhere in the region.
- cramfs bitfields flip with endianness, not just byte order: GCC packs them from the opposite end on a big-endian target, so a BE image is *not* a byte swap of an LE one (`read_inode` in `CramfsReader.cpp` spells out both). Its offsets count 4-byte units, so every structure is 4-aligned.
- A format with a strong magic that a reader can open belongs in `src/core/Swap.cpp`'s veto table. Without an entry, a small high-entropy file of that format (a bare `.bz2`) falls through to the text score, is analysed word-swapped, and is lost whole.
- **A checksum is what turns a weak magic into an extent.** Four formats now share the rule and it is the one to reach for next time: a GPT header whose signature was cleared is read because its CRC32 covers the signature bytes (`gpt-cleared-sig`); an unterminated tar claims only the bytes whose member headers verified; an Android super's partition map is described but claims nothing until the SHA-256 over its tables matches; and romfs refuses what its own validator refused. The shared failure they prevent is a magic-tier guess becoming bytes on disk -- romfs carved 1.87 GiB out of a blkid magic table before it applied this. A reader must re-apply its validator's rule rather than trust its caller.
- **Every cap has to track the evidence, and a cap that cuts is not the same as a cap that erases.** Two rules, learned from one bug. (1) `max_bytes` *and* `max_file_bytes` scale with the image (`extraction_budget`/`entry_budget` in `Recurse.cpp`, ratios in `core/Limits.h`; an explicit CLI flag clears the ratio and means the number exactly). The per-entry default was a flat 1 GiB, which cut two 1054 MiB SquashFS images out of the QNX dump at exactly 1,073,741,824 bytes -- and a SquashFS keeps its tables at the *end*, so each truncated copy walked to **zero files** and took ~74,000 files with it. A stored entry cannot exceed the image holding it, so a smaller cap can only ever cut real content; the bomb guard is `max_decompress_ratio` against the *compressed* size, which is the case a byte count cannot cover. (2) **A truncated entry is still an entry** (`Sink.h`): only `begin_file` refuses outright, and once bytes are on disk the entry must be counted, listed with digests over what landed, marked `truncated` and descended into. `emit_span_file` and `Sink::file` used to hand back a valid EntryResult *and* a failed Status, so all eight container readers plus cramfs and FAT dropped it -- leaving a file in the case directory that `listing.yaml` said did not exist.
- `analyze` will not fill the disk it writes to. `disk_headroom()` (`discovery/Recurse.h`) holds back 5% of free space, minimum 256 MiB; the extraction budget is cut once up front (`analyze-limit-disk`) and each carve is checked as it comes (`carve-limit-disk`), because `--max-carve-bytes` is per file and nothing else bounds carving in aggregate. The measurement is of the filesystem holding `--out`, which on a dev box is often tmpfs -- a case directory under `/tmp` fills RAM, which this project has already done once.
- **A Linux system's kernel and drivers are read from `lib/modules/<release>/`**, which answers both at once: the directory name *is* `uname -r` and everything under it is the module set. Nothing else inside a root filesystem does -- os-release says nothing about the kernel, and the `Linux version` banner lives in the kernel image, a *different node* a per-filesystem analyzer cannot see. Two layouts exist and the corpus has both: `make modules_install` writes `kernel/<subsystem>/...` (which classifies every driver for free) and OpenWrt writes one flat directory (where the subsystem is unknown and the module name is deliberately not guessed at). The release is the union of the directory entries and the modules' own first path component, because an archive built without directory members has no directories to list and an empty release directory has no module paths. A module's `vermagic` is a second, independent witness whose *disagreement* is the point (`platform-linux-kernel-mismatch`: modules built for another kernel do not load), and it carries the CPU architecture nothing else states -- `RLX` on the camera is a Realtek Lexra core. The analyzer stops at counting and corroborating; `artifacts`' `kmodule` extractor opens every module and parses `.modinfo` properly via `omnitrace::elf` (`core/Elf.h`), one record per driver with description, author, licence, depends and arch. `docs/{ANALYZERS,ARTIFACTS}.md`.
- **A kernel image is read for its banner and its symbols** (`artifacts`' `linux-kernel` extractor, `src/artifacts/kernel/`). The banner is the widely useful half: `Linux version ...` names the kernel, the toolchain and the build date, and is the *only* source for any of them when a system has no `lib/modules` -- all four corpus Linux images give one up. It has no magic behind it, so it earns its claim by the text after it parsing as a release: without that, the router-wrt image produced a kernel record from the sentence "Linux version of the hub software for the Direct Connect network", version `of`. The symbols come from **kallsyms**, the table `CONFIG_KALLSYMS` puts inside an image that is not an ELF. None of its four structures has a magic, so it is read *back to front* from `kallsyms_token_index`, the only self-describing one: entry *i* is the byte offset of token *i*, so the token table's position is solved rather than guessed -- but only to a shortlist, because a table of equal-length tokens satisfies the constraint shifted, and taking the first candidate and giving up is how a table gets missed. Everything earlier is pinned by a decode landing where the next structure starts (within one word: `names` is padded, and the camera leaves *eight* zero bytes before the token table, which read as "the marker array ends here"), and the result is accepted only when the names score as symbols. **Where the names begin is settled by the markers, not by `num_syms`**: marker k is the offset of symbol 256k, so a candidate start has to reproduce all of them, and anchoring on `num_syms` assumes the names follow it immediately -- the camera puts twelve bytes of padding there. Two counts then have to agree: trailing zero-length entries are padding, not symbols (every real name carries its type character), and the recorded `num_syms` is **required**, because reading an 8-byte marker array as 4-byte words yields a short chain a real names blob satisfies, decoding 511 genuine symbols out of 600 -- nothing in the names says the word size was wrong, the count beside them does. Router-nand decodes to 29,793 and the camera to 14,672. **Addresses are a second array** found by arithmetic (it sits immediately before the already-known `num_syms`) in one of three forms, and the test that tells them apart is that the *resolved* addresses ascend -- not the stored entries, which under `--absolute-percpu` fall as the addresses rise, so a check on them rejects exactly the form it was meant to find. Base-relative is tried first because its `relative_base` word sits where an absolute array's last address would be. Width matters as much as order: bounding a resolved address to the word size is what stops an absolute array being read as relative -- adding it to itself still ascends and still looks like addresses until a 32-bit kernel has a symbol at 0x10043b3c4. Router-nand is `relative`, base `0xc0088000`, `_stext` at `0xc0100000`; the camera is `absolute` at `0x80010400`, whose span is very nearly the payload itself. The two halves are found separately on purpose -- a table whose addresses fail still yields its names. The one corpus kernel with no symbols was built without CONFIG_KALLSYMS and says so. **The table is written out**, not just counted: `symbols/<node>-<entry>.txt` in the case, in `nm` format, because counting symbols is not having them and a disassembler already reads that format. Extractors do not write files -- the layer never touches the host filesystem and must keep working when re-examining a finished case -- so an extractor composes bytes and names a path (`artifacts::ExtractedFile`) and the caller places them, with every path checked by `safe_relative_path` because a file's *name* can come from evidence.
- **Phase 2 is complete.** Four post-analysis layers now run after `analyze()` builds the graph, and all of them depend on `core` (plus `output`) and never on `discovery` -- they take a list of `(node id, entries)` pairs, so a finished case can be re-examined without re-extracting it. `rules` (search packs) -> `analyzers` (what kind of system is this: Linux, QNX, Android) -> `artifacts` (parse a known file type into records: certificates) -> `report` (a typed Document rendered to HTML/Markdown, with the evidence re-hashed first). `docs/{RULES,ANALYZERS,ARTIFACTS,REPORT}.md`.
- **That decoupling is now spent rather than latent.** `output::load_case_listings` reads a case directory back into entries, and `omnitrace report <case>` re-runs the analyzers and the extractors over them. It rebuilds **all seven sections**: the search packs are the one thing not re-*run* (a sweep wants the image, not the case), so the hits are read back out of `artifacts.yaml` by `rules::artifacts_from_yaml` instead -- which means the section shows the sweep that happened rather than a second opinion about it. That reader refuses a document whose `summary.hits` disagrees with the number of `hits:` entries, because a file cut short while being written parses perfectly and would otherwise have a report print the smaller number as a finding. Measured on the 110,937-node QNX case: re-rendering a *copy* reproduces all seven sections byte-identically, 53,402 hits included. On the router corpus the Platforms and Extracted artifacts sections come back byte-identical to the ones `analyze` wrote. Two rules decide where an entry's bytes come from and both were found by watching the wrong thing happen: **the file beside the listing wins** over a recorded `host_path` that also exists (a case is routinely *copied*, and trusting the recorded path read the original's files while reporting on the copy), and **a path outside the case is never followed** (a case whose `files/` had been deleted produced records parsed out of a different case's bytes). The containment check is a path test, not a string prefix -- `<case>-copy` sits next to `<case>`. `docs/CASE_LAYOUT.md`, "Reading a case back".
- **A report names who is making its claims.** `--case-id` / `--examiner` / `--notes` on both `analyze` and `report`, kept in `Manifest::case_info` and written to `INFO.yaml` under an optional `case:` block, so re-rendering a case years later still names whoever ran it. It is a separate `CaseInfo` rather than more `RunInfo` fields because every `RunInfo` field is derived from the tool and can be checked against something, and none of these can: they are the examiner's statement, repeated as theirs. The block is written only when a field is set, so a case made without the flags is byte-identical to one made before they existed; a flag given to `report` overrides that one field and leaves the others, because adding a case number to an old case must not drop the examiner's name. `report --out DIR` writes the two files elsewhere and leaves the case untouched. These strings are escaped like any other -- a case number pasted from a system that allows anything is the threat model, not a hostile examiner.
- **Two cases are compared by path and by content, never by node id** (`src/diff/`, `omnitrace diff a b`, `docs/DIFF.md`). Ids are assigned in discovery order, so the same filesystem is `n000018` in one case and `n000021` in the other as soon as anything earlier in the image differs by a byte -- matching on them would report two acquisitions of one device as having nothing in common. The content view is what survives a rename: a moved file is one removal and one addition by path and neither by content, and the gap between the two numbers is the finding. Same for platform facts (keyed on the fact's name across every filesystem), for kernel symbols (compared by *name*, because addresses move whenever anything is recompiled), and for parsed records, which are keyed on `Artifact::identity` -- **set by the extractor, because only the extractor knows**: a certificate's SHA-256 fingerprint, a module's name, a kernel's banner. Not the path (moving `server.pem` is not issuing a certificate) and not the subject (a reissued certificate keeps one). Records are counted *distinct*, so `same + changed + only-in-A` equals the total; two files holding one certificate are one certificate. Lists are capped and **the totals are taken before the capping** -- reporting a capped list's length as the count is how a diff understates what it found. On the two camera releases it surfaces a telnet daemon in the newer one that the older does not ship, and the `8188fu` wireless driver rebuilt with a new srcversion; across two OpenWrt routers, a CA trust store holding 252 certificates on one and 148 on the other.
- **A case cannot be handed over as a directory.** `--tar-filesystems` writes `files.tar` beside every `files/` tree because an extracted tree copied onto a filesystem that is not POSIX loses symlinks, permission bits and any name that is not valid UTF-8, silently. Measured on a real handover to an exFAT drive: 1,348 symlinks refused, a QNX `phonebook.db` whose name carries raw bytes refused outright, and seven files whose evidence-preserved mode (`--w-r-----`) denies their own owner read -- rsync could not even read them to copy them. The archive is written by `DiskSink` from the *same entries* as the tree (`src/core/TarWriter.{h,cpp}`), in one pass, so it is faithful even where the host filesystem is not, and it records what was *written* rather than what the reader claimed: the size is patched into the header after the data, so a truncated entry says so. ustar with pax headers for long or non-UTF-8 names; the live tree only, never `.omnitrace-versions/`; byte-identical between runs, since nothing in it reads a clock or this host's passwd file. Roughly doubles a case on disk, which is why it is asked for. Note `--max-carve-bytes` (4 GiB) is separate and still skips larger partitions.
- **A report is data, never a concatenated string.** `src/report/` builds a typed `Document` and renders it once, because the previous generation shelled out to pandoc and that failed on provenance, escaping and determinism. A device's own bytes reach the markup: a partition named `<script>` and a certificate subject with a pipe in it are both attacker-controlled, and the renderers escape for their own format.
- Phase 2 has started with `src/rules/`: YAML search packs (`rules/*.yaml`, embedded like `signatures/*.toml`) compiled into one RE2 set. RE2 rather than `std::regex` because a pack is untrusted input and a backtracking engine can be hung by `(a+)+$`; it brings Abseil, which FetchContent builds in ~10s. Tune a new rule against the corpus before shipping it -- the first draft fired 581 times on one router's JavaScript (`docs/RULES.md`).
- **Sizing validators are the performance risk.** A validator that walks or decodes to find a structure's end runs on every magic hit, most of which are false. Screen the header cheaply first and read any forward search in chunks -- an unscreened byte-by-byte search took a scan of the QNX corpus from 12s to 2m49. `src/discovery/validators/zip.cpp` is the worked example.
- The contract every change must follow is `docs/ARCHITECTURE.md`. Read it before writing code. `docs/CODE_TOUR.md` explains the layers; `docs/EXTENDING.md` has step-by-step how-tos (validator, filesystem reader, container reader, CLI command, fixture, diagnostic code).
- Build: `cmake --preset linux-gcc && cmake --build --preset linux-gcc --parallel && ctest --preset linux-gcc`. Also keep `linux-clang` and `linux-asan` green. `CONTRIBUTING.md` covers setup on all OSes.
- Public headers under `include/omnitrace/` are the interfaces. Per-layer CMake globs sources and tests, so adding a file never needs a CMake edit.
- Output contract: the case directory in `docs/CASE_LAYOUT.md` (INFO.yaml, INFO.md, flash/, partitions/, mount.sh). `docs/reference/` holds generated catalogues (diagnostics, formats, attrs, CLI flags); regenerate with `scripts/gen_docs.py`, check with `scripts/check_docs.py`.
- Decisions on record: no web UI until the core is proven (`core-before-ui`); moria is a design reference and parity baseline only, never a dependency (`docs/MORIA_SPIKE.md`); GPT labels name carved partitions, nested finds are named by offset; third-party dependencies are allowed when they static-link (bzip2 was added on that basis; `vcpkg.json` plus a `find_package` in `cmake/Deps.cmake` plus the layer's `omnitrace_module(... DEPS ...)` plus a row in `CONTRIBUTING.md`).
- A parser two layers need lives in `src/core/` (`omnitrace::fdt` in `core/Fdt.h` is the worked example: the `dtb`/`fit` validators score a tree, `FitReader` extracts from it). A code assigned there and emitted from another layer is fine -- `scripts/gen_docs.py` joins the two halves across files.
- Diagnostic codes and attrs keys must be **literal** in the source. `scripts/gen_docs.py` cannot see a code built at run time (`format_ + "-failed"`), so it would reach manifests uncatalogued; use a layer-scoped literal (`container-decompress-failed`) when one reader serves several formats.
- `corpus/` is a local, git-ignored evidence corpus. Never commit images. Testing against it is described in `docs/TESTING.md`.
- **A regression check that compares nothing passes.** Three times in one session a corpus comparison reported success while both sides were empty: a `--max-bytes` too small for the nested nodes to exist, then a parser keyed on `format: tar` when the hits resolve as `also-matched`. Make the comparison hash the whole normalised manifest and refuse to report success when it found none of the thing under test.
